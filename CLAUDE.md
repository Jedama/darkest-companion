# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A companion web app for *Darkest Dungeon*: narrative events, character profiles/relationships, and AI-driven storytelling layered on top of the game's world. Solo hobby project (personal, non-commercial fan project). TypeScript throughout.

## Working with the project owner

The owner is new to Claude Code and to git/GitHub workflows generally (still learning things like branches, PRs, rebasing) — don't assume familiarity, and explain what a command or workflow step actually does rather than just running it.

- **Check in before diving in.** Prefer proposing an approach (or picking a task off `TODO.txt`) and pausing for a go-ahead before researching-and-fixing in one motion. More, smaller checkpoints are preferred over autonomously chaining a lot of actions together.
- **Show code in the chat itself**, not just via a tool call the owner has to expand — paste the relevant lines directly into the message when discussing a change.
- **Don't write or tune prompt text** (the LLM instruction files under `server/data/prompts/`) unless explicitly asked — the owner wants to keep authorship of these themselves, partly because AI editing prompts-for-AI tends to overcorrect for whatever specific issue prompted the edit.
- **PRs get squash-merged** on GitHub (owner's choice, done manually there) to keep `main`'s history clean — feel free to commit incrementally on a feature branch without worrying about tidiness there.

## Commands

This is two separate npm packages that must both be running for the app to work: the Vite/React frontend at the repo root, and an Express backend in `server/`. There is no root script that starts both — start them in two terminals.

```bash
# Frontend (repo root)
npm run dev       # Vite dev server
npm run build     # tsc -b && vite build
npm run lint      # eslint .
npm run preview   # preview a production build

# Backend (server/)
cd server && npm run dev   # tsx watch index.ts — auto-restarts on change
cd server && npm start     # node index.js (compiled)
```

There is no test framework wired up (no `test` script, no Jest/Vitest). `server/tests/_test_*.ts` are standalone scripts (not auto-discovered) that self-execute and print results to the console. Run one directly:

```bash
npx tsx server/tests/_test_council.ts
```

Some of these expect a fixture save file (`_test_estate.json`) generated by `_test_setup.ts`; they skip gracefully with a warning if it's missing.

Debugging LLM calls without spending tokens: set `LLM_MODE=stub` (or `fail`/`garbage` to exercise error paths) when starting the server, e.g. `LLM_MODE=stub npm run dev`. This can also be overridden per-request via `X-LLM-Mode`/`X-LLM-Delay` headers — this is what the frontend's debug panel uses to flip modes without restarting the server.

## Architecture

### Frontend/backend boundary
`src/utils/api.ts` is the *only* file allowed to call `fetch`. It talks to the server at `VITE_API_URL` (default `http://localhost:3000`, no Vite proxy configured) and unwraps the server's response envelope so callers only ever see the payload or a `ApiError` with a player-safe message. When changing what a route returns, this is the one frontend file that needs to change to absorb it.

### The estate is the save file
`Estate` (`shared/types/types.ts`) is the entire mutable game state for one playthrough — roster, leadership, followUps queue, narratives, time/weather, etc. It's persisted as JSON per-estate under `server/data/estates/` (gitignored) via `server/fileOps.ts`.

Because routes can `await` a slow LLM call mid-request, a naive load→mutate→save has a race window where a second concurrent request can clobber the first's write. `server/estateLock.ts`'s `withEstate(estateName, mutate)` serializes the load→mutate→save cycle per estate name (a promise-chain queue, not a real lock) and is how every write-path route should touch an estate. Read-only routes (story, planning, static data) skip the lock entirely.

### Static game data vs. save data
`server/staticGameDataManager.ts` (`StaticGameDataManager`, a singleton) is the in-memory registry of everything that's design content rather than player state: character templates, locations, NPCs, enemies, event templates, prompts, keywords. It's loaded once from JSON under `server/data/` (`templateLoader.ts` for game data, `promptRegistry.ts` for prompt text) via `.initialize()` before the server starts accepting requests (`server/index.ts`). Services read from this singleton rather than hitting disk themselves.

### Town events span three requests
A town event (setup → story → consequences) is not a single atomic action — it's three separate HTTP round-trips (`server/routes/setupEventRoute.ts`, `storyEventRoute.ts`, `consequencesEventRoute.ts`), because the story text has to exist before consequences can be requested, and each step can independently fail or have its modal closed. Anything that needs to survive across those three steps (like a reserved follow-up event) uses an explicit "reserved but not yet consumed" field on the estate rather than assuming the whole flow completes — see `server/services/game/followUpService.ts`'s `inFlight` reservation model for the pattern.

### Follow-up events
The monthly review LLM call (`server/services/review/reviewService.ts`) can propose follow-up events, which get queued (`followUpService.ts`) and probabilistically preferred over random events for a few subsequent town events (decaying chance, front-skewed queue position). Follow-up fields (including `location`) come directly from LLM output, so `addFollowUpEvent` is the validation point for that data before it enters the estate — a location id that doesn't exist in the real location map is corrected there rather than being allowed to degrade silently later in location scoring.

### Location scoring
`server/services/game/locationService.ts` picks where an event happens by scoring every candidate location for a given cast (residence/workplace/frequent haunts, shared-location bonus, optional parent-location fallback) and weighted-randoming over the result. It's guaranteed to return *something* even for a cast with no location data (falls back to the general town pool), so callers upstream should validate location ids proactively rather than relying on this fallback to catch bad input.

### LLM layer
`server/services/llm/`: `llmMode.ts` decides per-request whether calls are live/stubbed/deliberately-failing, carried via `AsyncLocalStorage` (not a module-level variable — needed because concurrent requests would otherwise clobber each other's mode). `buildPromptService.ts` assembles prompt sections from estate state; `estateLlm.ts`/`llmService.ts` make the actual provider calls; `llmStub.ts` provides canned responses for `stub` mode; `llmResponseProcessor.ts` and `consequenceChecks.ts` parse/validate what comes back.

### Politics & town hall
`server/services/politics/` computes the social graph between characters (cliques, relationships, hero/political metrics) used to color events and dialogue. `server/services/townHall/` handles council elections and expedition party planning; `expeditionStrategies/` is a registry of named scoring strategies (e.g. `maximizeAffinity`, `minimizeDiscord`) that combine into a party-picking weight — `strategyRegistry.ts` is the source of truth for what strategies exist and their defaults.

### Shared code
`shared/types/types.ts` and `shared/constants/` are imported by both the frontend and `server/`, so a type or constant change there affects both packages — check both when editing.
